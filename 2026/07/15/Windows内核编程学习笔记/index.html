Windows内核编程学习笔记

内核编程环境及其特殊性

内核层环境

CPU内核层分4个权限等级，分别是Ring3，Ring2，Ring1，Ring0，但是实际上只有两个层级3和0，Ring3即是用户层，Ring0即是内核层

Windows使用双模式保护操作系统，应用程序的代码运行在用户模式下，而系统的内核和内核的扩展模块，也就是内核驱动程序都在内核层内

内存也分为内核空间和应用空间，用户空间占用低位地址，内核空间则占用高位地址，在物理内存中，内核空间的代码和核心数据结构只有一份副本，所有应用程序在进入使用内核内容时，使用的都是这同一份物理内存。但是在现代操作系统中，每个应用的进程虚拟地址空间是独立的，所有应用都认为自己有独立的内核空间，实际上它们使用的是同一个物理的内存地址

内核空间代码作为R0代码执行，不受任何限制，编写内核模块，需要使用微软提供的WDK进行编写，以及安装IDE VS和SDK

由于内核编程会影响到操作系统，因此在虚拟机中进行学习是必要的，学习都在win10 x64虚拟机内进行

数据类型的特殊性

基本数据类型

在进行内核编程时，为了防止64位和32位储存冲突，因此定义变量通常不用惯用的unsigned int和long之类的，而是改为了WDK的编程规范标准

  • unsigned int 重定义为ULONG
  • unsigned char 重定义为UCHAR
  • unsigned int 重定义为UINT
  • void 重定义为VOID
  • unsigned long * 重定义为PULONG
  • unsigned char * 重定义为PUCHAR
  • unsigned int * 重定义为PUINT
  • void * 重定义为PVOID

返回类型

绝大多少的内核API返回的都是一个状态，一些常用的状态为

  • STATUS_SUCCESS //成功

  • STATUS_INVALID_PARAMETER //错误参数

  • STATUS_INSUFFICIENT_RESOURCES //资源不足（内存不足之类）

  • STATUS_PENDING //请求未决

  • STATUS_BUFFER_OVERFLOW //缓冲区不足

  • STATUS_BUFFER_TOO_SMALL //缓冲区不足

字符串

在内核编程中的字符串一般用一个结构来进行容纳，结构为UNICODE_STRING，并且这个字符串是双字节的（可以从UNICODE）看出来

重要的数据结构

驱动对象

内核认为驱动设备之类的都是一个对象，一个驱动对象代表了一个驱动程序,驱动对象DRIVER_OBJECT

这个对象并不是cpp式的类，而是c利用结构体模拟的对象，在这个结构体中，几个关键的部分

  • PVOID DriverStart //这个模块在内核空间里的开始地址
  • ULONG DriverSize //这个模块在内核空间里的大小
  • UNICODE_STRING DriverName //驱动名字
  • PDEVICE_OBJECT DeviceObject //链表头指针，指向这个驱动所创建的第一个设备对象
  • PFAST_IO_DISPATCH FastIoDispatch //快速IO分发函数
  • PDRIVER_UNLOAD DriverUnload //驱动的卸载函数
  • PDRIVER_dispatch MajorFunction[IRP_MJ_MAXIMUM_FUNCTION +1] //普通分发函数

在这其中，PDRIVER_dispatch MajorFunction[IRP_MJ_MAXIMUM_FUNCTION +1]和PDRIVER_UNLOAD DriverUnload是将内核的所有功能提供给Windows的，在这里只需要知道，前者要慢一点，而后者比较快一些就行了

设备对象

设备对象DEVICE_OBJECT总是属于一个驱动对象，由驱动对象生成设备对象，当Windows向设备发送请求时，这个请求实际上是被驱动对象捕获，然后由分发函数分发给设备对象

设备对象结构体里的关键内容：

  • struct _DRIVER_OBJECT *DriverObject //这个设备所属的驱动对象
  • struct _DEVICE_OBJECT *NextDevice //下一个设备对象，在一个驱动对象中有多个设备，这些设备通过链表的指针来连接
  • DEVICE_TYPE DeviceType //设备类型
  • HAR StackSize //IRP栈大小
  • ULONG ReferenceCount //引用计数，记录有多少个内核组件在使用这个设备对象

请求

大部分的请求以IRP的形式发送

IRP：I/O Request Packet的缩写，I/O请求包，内核中大部分请求都以IRP的形式传递，而任何一个IRP都是发送给一个设备对象的

IRP也是一个内核数据结构，这个结构比较复杂，初步了解的内容：

  • PMDL MdlAddress //内存描述符指针，大概可以理解为描述缓冲区来给请求使用

  • union{

    ​ struct _IRP *MasterIrp;

    ​ __volatile LONG irpCount;

    ​ PVOID SystemBuffer;

    }AssociatedIrp; //这个共用体是比MdlAddress简单点的表示缓冲区的方式，是S有stemBuffer具体使用哪种要看要看请求的IO方式

  • IO_STATUS_BLOCK IoStatus; //IO状态，一般请求完成后的返回情况放在这里

  • CHAR StackCount; //IRP栈空间大小

  • CHAR CurrentLocation; //IRP当前栈空间大小

  • __volatile PDRIVER_CANCEL Cancel Routine; //用于取消一个未决请求的函数

  • PVOID UserBuffer; //和MdlAddress和SystemBuffere一样都表示缓冲区，但是特性不同

函数调用

大部分内核API都有前缀，主要的函数都以Nt,Zw,Io,Ex,Rtl,Ke,Ps开头，具体的学习一些函数是不现实的，但是通过这些函数的开头，可以将它们这样分类

  • Nt/Zw:系统服务
  • Io:io管理器，创建删除设备对象，发送IRP，注册中断，操作硬件端口
  • Ex:执行体，管理内存堆内存分配，同步锁
  • Rtl:运行时库，字符串处理，内存拷贝，算法计算
  • Ke:内核核心，控制线程调度操纵内核事件
  • Ps:进程和线程管理

代码的中断级

用户态R3编程没用中断级概念，所有中断都处于同一级，但是在内核编程中，运行的代码有不同的中断级，主要有Passive和Dispatch两种，后者大于前者，具有比较复杂的功能的API都要求在Passive执行，比较简单的函数在Dispatch执行

第一次实践

安装win10双机调试环境，尝试第一次windbg调试
在主机上安装windbg，虚拟机调试机为 Windows 10 Enterprise LTSC 2019

字符串 链表 自旋锁

字符串

内存和链表

在c里分配内存通常用malloc，在内核编程中常使用ExAllocatePoolWithTag

ExAllocatePoolWithTag分配的内存由ExFreePoll来释放，如果不释放会永远泄露，只有重启计算机才会恢复

LIST_ENTRY是开发者开发的链表数据结构，是一个双链表

自旋锁

在内核编程中，使用KSPIN_LOCK数据结构获得一个自旋锁

例如：KSPIN_LOCK my_spin_lock;

​ KeInitializeSPinLock(&my_spin_lock);

使用时要定义一个KIRQL来作为自旋锁的中断等级，开始锁定线程的操作是KeAcquireSpinLock,结束的是KeReleaseSpinLock,使用时例如KeAcquireSpinLock(&my_spin_lock,&irql);此时中断等级会升级

重要的是，只有一个线程能获得自旋锁，其它线程都会被锁住，因此如果在一个函数里写了自旋锁，要注意是只给一个线程调用，避免所有线程都定义了一个自旋锁

文件操作

在内核编程里，打开文件必须先使用OBJECT_ATTRIBUTES结构，这个结构通常会被InitializedAttributes初始化，无论是打开文件打开注册表键还是打开设备都会先调用InitializedAttributes初始化一个OBJECT_ATTRIBUTES

打开文件使用ZwCreatFile函数,读写文件用ZwReadFile, ZwWriteFile函数

注册表操作

打开注册表键ZwOpenKey

读取注册表中键ZwQueryValueKey

写注册表值ZwSetValueKey

时间和定时器

内核编程中获得系统启动后经历的滴答数的函数是KeQueryTickCount

获得系统时间KeQuerySystemTime，这个时间不少当地时间，要使用ExSystemTimeTolocalTime转换成当地时间，还需要通过RtlTimeToTimeFields来转换位人可以阅读的时间

使用定时器KeSetTimer

线程与事件

驱动里的线程一般是系统线程，而系统线程所在的进程是System（就是每次任务管理器里的那个）

R3的sleep函数可以使程序停下，在内核编程里使用KeDelayExecutionThread函数进行睡眠

应用和内核通信

创建设备对象

应用层的软件想要获得日志或者操控驱动之内的功能，需要和内核层进行通信，首先要生成一个设备对象，设备对象可以在内核中暴露出来给应用层，应用层则可以操作它，使用IoCreateDevice来生成一个设备对象

但是，IoCreateDevice生成出来的设备需要有管理员权限才可以打开它，另一个强迫生成任何用户都能打开的设备是IoCreateDeviceSecure，不过这并不安全

对象链接

应用层不能直接使用设备对象名字来进行链接，设备和应用层的链接需要通过符号链接，生成这个符号的函数是IoCreateSymbolicLink

但是，使用符号链接还是难免出现问题，如果和其它驱动的符号字符串相同，那么就会出现问题，最现代正常的方法是访问设备对象（IoCreateDeviceSecure)结构体创建时的GUID，这个id可以保证全球唯一

生成了设备和符号后，在卸载驱动的时候就要删除它们，不然符号链接就会一直存在，要依次删除符号链接和控制设备

分发函数

分发函数设置在驱动对象上，由驱动分发给自己的子设备对象，核心的分发函数即是cwkDispatch，这个函数只包含了发送对象和irp请求的指针

分发函数处理请求第一步是获得请求当前的栈指针，然后判断发给谁，再进行判断请求的种类

应用和驱动之间的通信

应用层与驱动层之间的通信，应用层通过CreateFile，然后使用DeviceIoControl来引起内核程序的反应，内核主动通信应用层可以通过共享句柄来实现

提供用户态通信接口的驱动程序很容易暴露除内核漏洞，因此为了防止被攻击，要进行测试，例如

  • 输入缓冲区很小会怎么样
  • 输入缓冲区很大会怎么样
  • 输入缓冲区刚好等于规定的最大或最小长度会怎么样
  • 如果输入的是字符串，如果字符串没用结束符怎么样
  • 如果字符串长度为0会怎么样

64位和32位差异

在64位系统运行32位程序时，windows的解决方案是使用WOW64子系统，当32位程序执行时，WOW64子系统会拦截32位程序的系统调用，将这个程序里的参数，转换成适合64位系统的长度

同样的，如果32位程序需要调用32位的dll，也会使用WOW子系统的SysWOW64目录dll而不是System32里的64位dll，这里是WOW64的文件系统重定向功能

PatchGuard

32位系统中，驱动程序可以直接对内核的数据结构和关键的函数进行挂钩和修改，但是在windows 64位系统里引入了PatchGuard技术

PathcGuard会定时检查系统关键的位置，例如SSDT系统服务描述表，GDT全局描述表，IDT中断描述表，系统模块，如果发现这些内容代码数据被修改，就会立马蓝屏，因此在32位上能实现的一些HOOK技术在64位系统下都无法使用

PatchGuard避免了内核遭到恶意的模块破坏，但也阻碍了一些功能的实现，这个功能对游戏安全方向很重要，需要重点了解下

context 结构体

检测通常基于 context 结构体，context 结构体是一个内存数据结构，包含了系统内核的重要信息，包括内核代码的状态、配置和数据，Patch Guard 使用这个 context 结构体来验证内核代码的完整性，在系统启动时，PG 会创建并存储 context 结构体，并在系统运行过程中定期检查这个结构体是否被修改，如果发现任何不正确的修改，Patch Guard 将会重启系统以确保安全性

context规则（随版本不同规则有变）：

  • context大部分时间处于加密状态
  • context的数据源来自系统初始化时的最初数据
  • context的地址作为系统线程，随着DPC等调度被传递
  • context的执行周期约为2min，但是每次检测的目标区块是随机的
  • context采用接力的方式调度，具体流程包括自解密、检测逻辑、复制自身到新的context、加密新context、销毁旧的context
  • context检测逻辑的调用源有随机性，在PG初始化时决定

攻击方法

  • 静态补丁：直接把函数入口patch为ret
  • VT读/执行分离：在现代win11上已经失效
  • 定位所有context的调用源：针对性patch，修改代码的特定部分来避免检测
  • 对context进行解密：解密context内容，修改检测代码
