JWT对称加密弱密匙

我们之前在基础知识的时候说到，JWT使用了两种加密算法，HS256(对称加密)以及RS256(非对称加密)。既然有对称加密，那必然有密钥。

当密钥使用了常见的字符串以及默认字符串，那么这个时候，我们就可以进行伪造。比如：111111，admin等

HS256（对称加密）

建议密钥长度：至少 32 字节（256 位） HS256 使用 HMAC-SHA256 算法，理论上密钥长度应与哈希输出长度（256 位）匹配以保证安全性。实际应用中推荐使用 32 字节或更长的随机密钥（如 64 字节），避免使用弱密钥或可预测字符串。

RS256（非对称加密）

建议密钥长度：至少 2048 位（推荐 4096 位） RS256 使用 RSA 签名算法，基于整数分解难题。当前安全标准要求 RSA 密钥至少 2048 位（可提供约 112 位安全强度）；若需长期安全性（如 10 年以上），建议使用 4096 位密钥。

JKU 远程公匙加载

JKU（JWT Set URL）是 JWT 头部的一个扩展字段，作用是指定远程公钥的下载地址，让服务端自动从远程服务器拉取 JWK（JSON Web Key）公钥，完成 JWT 验签。

这是微服务、SSO、第三方授权场景中最常用的自动公钥管理方案，无需手动配置公钥。

验签流程：

  • 解析 JWT 头部 → 提取 jku + kid（密钥 ID）
  • 调用 jku 地址下载 JWKS
  • 根据 kid 匹配对应公钥
  • 使用公钥验证 JWT 签名

JWT公钥泄露+算法混淆

攻击者拿到公钥后，可将非对称签名（如 RS256）篡改为对称 HMAC（如 HS256），用公钥当密钥伪造任意有效 Token，直接绕过身份校验、越权访问。

算法 类型 签名 & 验签逻辑 密钥安全要求
HS256 对称加密 同一个密钥同时用于签名和验签 密钥必须全程保密，泄露即可伪造签名
RS256 非对称加密 私钥仅用于签名，公钥仅用于验签 私钥严格保密，公钥设计上可公开

漏洞逻辑

  1. 服务端原本使用 RS256 非对称算法，仅持有公钥用于验签，私钥由认证中心保管；
  2. 开发未严格校验 JWT Header 中的alg字段，完全信任客户端传入的算法声明，未强制固定验签算法；
  3. 攻击者将 JWT Header 中的alg从RS256改为HS256，诱导服务端切换为对称算法验签逻辑；
  4. 服务端收到篡改后的 JWT 后，会按照alg=HS256的逻辑，把手中的 RSA 公钥当作 HS256 的对称密钥进行验签；
  5. 攻击者通过泄露的公钥，直接用该公钥作为 HS256 的密钥，对篡改后的 Header+Payload 生成签名，服务端验签完全匹配，伪造的 JWT 被合法认可。

知识点：

  • 标准 JWKS 端点暴露：/.well-known/jwks.json（OAuth2 体系默认公开接口）；
  • 还有一种可能性是直接在/jwks.json

例如拿到公钥后，在JWT Editor里新建RSAkey，将得到的内容（只要key文件夹内的）进去，并且转成PEM格式，将PEM格式的内容转换成BASE64，再创造对称密匙，key输入内容，再在传包时，选择用HS256和提权，用对称密匙签名即可

JWT算法混淆+公钥推导

  1. RS256：非对称加密，用私钥签名、公钥验证
  2. 算法混淆：服务端错误把 RS256 当成 HS256（对称加密），用公钥作为 HMAC 密钥验证
  3. 公钥推导：通过 2 个合法 RS256 JWT，利用 RSA 数学特性计算出公钥n(模数)

注意以上条件缺一不可。

面试题目

什么是JWT？它的结构是怎样的？

  • JWT（JSON Web Token）是一种用于身份验证和信息传递的无状态令牌，由Header、Payload、Signature三部分组成，格式为Header.Payload.Signature。
  • Header：说明令牌类型和签名算法（如{"alg":"HS256","typ":"JWT"}）
  • Payload：存放实际数据（用户ID、角色、过期时间等）
  • Signature：对前两部分的签名，防止篡改

深度扩展：

  • 对比Session认证：JWT无需服务器存储状态，适合分布式系统
  • 强调Header和Payload仅是Base64编码，未加密，敏感信息不应放在Payload中

JWT的签名算法有哪些？对称与非对称的区别？

标准答案：

  • 对称算法：HS256（HMAC + SHA256），使用同一个密钥进行签名和验证
  • 非对称算法：RS256（RSA + SHA256），私钥签名，公钥验证
  • 其他：ES256（ECDSA）、PS256等

深度扩展：

  • 解释算法混淆攻击的原理：服务器预期用RS256，攻击者改为HS256，并用服务器公钥作为HMAC密钥
  • 提及alg: none漏洞：早期JWT库支持无签名算法

JKU注入和JWK注入的区别？

标准答案：

  • JWK注入：直接在JWT Header中嵌入jwk字段，包含攻击者的公钥
  • JKU注入：在Header中设置jku字段，指向一个URL，服务器从该URL获取JWKS公钥集
  • 关键区别：JWK是内联公钥，JKU是远程获取公钥集

深度扩展：

  • 攻击条件：服务器未验证JKU来源的合法性
  • 防御：限制JKU域名白名单、不信任用户提供的JKU

如何有效防御JWT漏洞？

标准答案：

  1. 强制算法白名单：只允许预期的算法（如只接受HS256）
  2. 严格过滤Header参数：不信任客户端传来的alg、kid、jku等
  3. 实施零信任后端验证：
  • 始终验证签名，即使alg为none
  • 密钥与算法绑定（HS256用对称密钥，RS256用非对称密钥对） 4. 安全配置：
  • 使用强密钥，定期轮换
  • 设置合理的过期时间（exp）
  • Payload不存放敏感信息

你在实战中如何检测JWT漏洞

  1. 识别JWT：在Cookie或Authorization头中寻找eyJ开头的字符串
  2. 解码分析：用jwt.io或Burp插件查看Header和Payload
  3. 测试点检查：
  • 修改alg为none → 空算法漏洞
  • 修改Payload数据（如role:admin）→ 未验证签名
  • 查找公钥端点（/jwks.json）→ 算法混淆可能
  • 检查kid/jku参数 → 注入漏洞
  • …这里参考上述漏洞 4. 工具辅助：Burp的JWT Editor插件、jwt_tool

如果发现JWT使用弱密钥（如”secret”），如何利用

  1. 使用字典爆破密钥（工具：hashcat、jwt-cracker）
  2. 爆破成功后，用该密钥重新签名伪造的Payload
  3. 实现越权访问（如普通用户→管理员）
